По итогам всего нашего анализа — вот финальный, предельно эффективный стек для **data-driven** и **stream-first** архитектуры полномасштабного сбора данных. Это не просто набор инструментов, а **взаимосвязанная система**, где каждый слой усиливает остальные.

---

### 🏗️ Слой 1: Полномасштабный сбор данных

*   **Common Crawl**: Единственный публичный, аудируемый краулер веб-масштаба. Архив с 2008 года превышает **10 ПБ**.
*   **Heritrix (Internet Archive)**: Java-краулер для крупномасштабного архивирования (накопил **400 ТБ**).
*   **Apache Nutch + Hadoop**: Классическая связка для петабайтного краулинга, проверенная десятилетиями.

### ⚡ Слой 2: Event Transport — Redpanda (не отказываемся)

**Redpanda** остаётся оптимальным выбором для транспорта событий, и вот почему:

*   **p99 latency 1–2ms против 5–20ms у Kafka**: Redpanda написан на C++ с thread-per-core моделью, что устраняет JVM GC-паузы и даёт предсказуемую задержку.
*   **Операционная простота**: Один бинарник, один процесс — нет ZooKeeper и JVM. Это радикально снижает операционную сложность.
*   **Эффективность ресурсов**: Redpanda требует примерно на **60–87% меньше узлов** для той же нагрузки, чем Kafka (Teads saw an 87% reduction in brokers).
*   **Совместимость с Kafka API**: Все существующие Kafka-клиенты, коннекторы и инструменты работают без модификаций.

**Почему не Kafka?** Kafka 4.0 с KRaft закрыл разрыв по ZooKeeper, но JVM GC-паузы остаются фундаментальной проблемой, вызывающей p99-спайки до 50–200ms под нагрузкой. Для stream-first архитектуры это неприемлемо.

**Почему не Pulsar?** Pulsar архитектурно элегантен (разделение compute/storage через BookKeeper), но на практике его производительность ниже, а операционная сложность выше: он использует 3 уровня, что делает его дороже в эксплуатации, чем Kafka.

### 📦 Слой 3: Stream Storage для аналитики — Apache Fluss (дополнение, не замена)

**Ключевое уточнение**: Fluss — это **не замена Redpanda**, а **дополнительный слой хранения**, который делает streaming-данные одновременно доступными для low-latency приложений и аналитических систем.

*   **Колоночное хранение**: В отличие от log-based модели Kafka/Redpanda, Fluss хранит данные в колоночном формате, что ускоряет аналитические запросы до 91 раза.
*   **Плотная интеграция с LakeHouse**: Fluss спроектирован для тесной интеграции с Apache Iceberg и Apache Paimon. Это означает, что данные, записанные в Fluss, могут напрямую использоваться в lakehouse без дополнительного ETL.
*   **Production-готовность**: Alibaba уже запустила Fluss в production с **3 ПБ данных при 40 ГБ/с**. Развернут в阿里巴巴、小红书、京东、蚂蚁集团、Fresha、爱奇艺等公司的生产环境中.

**Архитектурный паттерн**: Redpanda → Flink → Fluss. Redpanda обеспечивает транспорт и буферизацию, Flink — обработку, Fluss — хранение для аналитики.

### 🌊 Слой 4: Потоковая обработка — Apache Flink

**Apache Flink** остаётся де-факто стандартом для потоковой обработки:

*   **Масштаб**: Uber использует Flink для петабайтных операций, Alibaba — **4 ПБ/день при 1 млрд TPS**.
*   **Dynamic Iceberg Sink**: Flink может динамически создавать и писать в Iceberg-таблицы на основе инструкций в самих записях, автоматически эволюционируя схему без перезапуска job'а.
*   **Exactly-once semantics**: Flink обеспечивает гарантию ровно однократной обработки, управляя транзакциями и обеспечивая консистентность данных.

### 🗄️ Слой 5: Data Integration — Apache Gobblin

**Apache Gobblin** — это фреймворк для интеграции данных корпоративного уровня, который управляет полным жизненным циклом данных:

*   **Универсальный ingestion**: Поддерживает не только Kafka, но и множество других источников, с возможностью легкого добавления новых.
*   **Production-проверка**: Используется в LinkedIn, PayPal, Verizon на петабайтных масштабах.
*   **Управление жизненным циклом**: Компактификация, дедупликация и удаление данных в соответствии с требованиями (например, GDPR).

**Почему не Kafka Connect?** Kafka Connect — это транспортный слой, а Gobblin — это **система управления данными**. Если нужно не просто перекачать данные, а построить управляемое и соответствующее требованиям хранилище, Gobblin — более системное решение.

### 💾 Слой 6: Хранение и индексация

#### Apache Iceberg (Table Format)
Iceberg становится **универсальным стандартом** для озера данных. Flink пишет в Iceberg напрямую, обеспечивая ACID-транзакции и schema evolution.

#### Quickwit (Поисковый движок)
Quickwit — это **специализированный поисковый движок для immutable данных** (логи, трассировки, audit events) на петабайтном масштабе:

*   **S3-native архитектура**: Поиск выполняется **напрямую в объектном хранилище** с субсекундной задержкой.
*   **10-кратная экономия**: Снижение инфраструктурных затрат по сравнению с Elasticsearch за счет отказа от дорогих локальных storage-тиров.
*   **Производительность**: 1 ПБ/день скорость индексации, субсекундный поиск по 50 ПБ данных.

#### DeltaCAT (Exabyte Lakehouse)
**DeltaCAT** на Ray обеспечивает **экзабайтную масштабируемость** и ACID-совместимый CDC:

*   **Exabyte-scale**: Успешно используется для управления экзабайтными корпоративными озерами данных.
*   **Ray-powered**: Использует распределенный compute-фреймворк Ray вместе с Apache Arrow и Daft для эффективного масштабирования.

#### TernFS (Файловая система для экзабайтов)
**TernFS** — распределенная файловая система, созданная XTX Markets для работы с экзабайтными объемами:

*   **Масштаб**: 500+ ПБ данных на 30 000 HDD и 10 000 SSD в 3 дата-центрах.
*   **Дизайн**: Оптимизирован для **immutable файлов** (ML-датасеты, логи, архивы), с поддержкой до 10 ЭБ логического хранилища, триллиона файлов и миллиона клиентов.


### 🔧 Вспомогательные прослойки

#### 1. Оркестрация и управление пайплайнами
*   **Dagster**: Рекомендуется для ML/AI, лучший data lineage. Dagster assets — это plain Python, можно unit-тестировать трансформации без инфраструктуры.
*   **Apache Airflow**: Проверенный enterprise-стандарт для сложных, детерминированных batch-процессов. Bloomberg выбрал Airflow за широту Python-интеграций и способность обрабатывать сложные мультисистемные workflows.
*   **Temporal**: Для сложных, долгоживущих workflows с гарантией выполнения.

#### 2. Качество данных
*   **Great Expectations**: Python-native, 300+ встроенных expectations (types, ranges, regex, distributions). Для команд с Python-heavy стеком.
*   **Soda Core**: YAML-ориентированный, SodaCL быстрее в 22 раза чем GX для staged-стратегии. Для SQL-heavy стеков и быстрого time-to-first-scorecard.

#### 3. Метаданные и Lineage
*   **DataHub**: Apache-2.0, mature lineage на LinkedIn scale, column-level lineage для большинства major warehouses, графовая визуализация обрабатывает тысячи узлов без choking.
*   **OpenMetadata**: Apache-2.0, lineage значительно догнал DataHub, column-level lineage. 90+ нативных коннекторов.
*   **OpenLineage**: Открытая спецификация для сбора метаданных о происхождении.

#### 4. Реестр схем
*   **Confluent Schema Registry**: Референсная реализация для Kafka.
*   **Apicurio Registry**: Open-source альтернатива, поддерживает Avro, Protobuf, JSON Schema.
*   **Karapace**: Open-source от Aiven.

#### 5. Наблюдаемость данных
*   **Monte Carlo**: ML-ориентированное обнаружение аномалий и автоматическое профилирование всех таблиц.
*   **Elementary**: Open-source инструмент, работающий внутри dbt-проекта.
*   **Metaplane**, **Bigeye**, **Anomalo**: Для команд с фокусом на конкретных СУБД или нулевой настройке.

#### 6. Безопасность и управление секретами
*   **HashiCorp Vault**: Де-факто стандарт для безопасного хранения и ротации ключей/паролей. Интеграция с Kafka и Kubernetes для предоставления временных доступов.
*   **Шифрование**:
    *   **В движении**: TLS/SSL для всего трафика.
    *   **В покое**: Customer Managed Keys (CMK) в облачных KMS (например, AWS KMS).
    *   **На уровне полей**: Client-Side Field Level Encryption (CSFLE) для шифрования чувствительных полей еще на стороне продюсера.

#### 7. Управление конфигурациями (Configuration-as-Code)
*   **Terraform**: Для декларативного описания и управления ресурсами (CDC-коннекторы, топики Kafka, вычислительные ресурсы).
*   **GitOps**: Для применения конфигураций через CI/CD и автоматического обнаружения дрейфа (drift detection).

#### 8. API-шлюз для доступа к данным
*   **Kong**: С поддержкой стриминга для real-time обработки.
*   **Tyk**: Специализированный модуль Tyk Streams для управления event-driven API.
*   **Облачные шлюзы**: Amazon API Gateway, Alibaba Cloud API Gateway с поддержкой SSE и WebSocket.

#### 9. Мониторинг и алертинг инфраструктуры
*   **Prometheus**: Для сбора метрик.
*   **Grafana**: Для визуализации и настройки алертов.
*   **Alertmanager**: Для управления уведомлениями.

#### 10. Управление данными (Data Governance) и Data Mesh
*   **Confluent Stream Governance**: Набор практик и инструментов для управления данными в движении, включая Stream Lineage, Stream Catalog, RBAC и CSFLE.
*   **Data Mesh Control Plane**: Выделенный управляющий слой для управления пайплайнами и данными, отделенный от плоскости исполнения (data plane).

### 🎯 Ключевые выводы

1.  **Redpanda остаётся**: Для stream-first архитектуры Redpanda — оптимальный транспорт с p99 1–2ms, без JVM и ZooKeeper.
2.  **Fluss — дополнение, не замена**: Fluss добавляет колоночное хранение и интеграцию с lakehouse, но не заменяет транспортный слой.
3.  **Gobblin вместо Kafka Connect**: Для управления жизненным циклом данных на петабайтном масштабе.
4.  **DeltaCAT + TernFS для экзабайтов**: Когда петабайтов уже недостаточно.
5.  **Quickwit для поиска**: S3-native, 10-кратная экономия, субсекундный поиск по петабайтам.
6.  **DataHub для lineage**: Mature lineage на LinkedIn scale, column-level lineage, графовая визуализация обрабатывает тысячи узлов.
7.  **Dagster для оркестрации ML/AI**: Лучший data lineage, asset-based pipeline design.

Эта архитектура представляет собой **открытую, модульную и масштабируемую платформу**, способную собирать, обрабатывать и анализировать информацию в **петабайтных и экзабайтных** масштабах. Ключевое отличие от классических архитектур — **отказ от Kafka в пользу Redpanda** как транспортного слоя с p99 1–2ms, и **добавление Fluss** как stream storage для аналитики, что даёт **10-кратную экономию** на хранении и **до 91 раза быстрее** аналитические запросы.
